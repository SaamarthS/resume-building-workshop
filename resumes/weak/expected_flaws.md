# John Doe Resume: Expected Flaws Answer Key

> **Facilitator Reference:** Use this guide during the opening 0–5 minute critique exercise. Students are challenged to spot flaws within 20 seconds. They do not need to spot every flaw immediately; use this key to guide discussion.

---

## Pedagogical Context & Core Rule

* **Visuals are NOT the flaw:** John Doe's resume layout is clean, well-spaced, and legible. Do *not* tell students the resume looks ugly. The lesson is that **a clean format does not rescue empty content**.
* **Zero Fabrication:** The source material does not provide additional facts, metrics, or personal achievements for John Doe. When building the improved version, demonstrate stronger phrasing and structural improvements without inventing fictitious metrics (e.g., do not claim John "served 100,000 users" if he never did).

---

## 10 Major Diagnostic Flaws

### 1. Too Many Skills, With No Categories
* 15 technologies listed in a single comma-separated line.
* Languages, frameworks, databases, platforms, and developer tools are jumbled together.
* Gives no indication of proficiency or focus.
* Listing a technology does not demonstrate competence; John cannot realistically defend all 15 in a technical interview.

### 2. Generic Project Descriptions
* *"Made a website using React and Node"* — provides zero insight into architecture, purpose, or complexity.
* *"Created a machine learning model using Python"* — fails to state the disease targeted, data used, algorithm, or evaluation metric.
* *"Built a to-do list using HTML, CSS and JavaScript"* — elementary tutorial project with no depth.
* Bullets omit technical decisions, challenges overcome, and John's personal contributions.

### 3. No Evidence of Results or Impact
* No outcomes, evaluation scores, demonstrations, or technical milestones.
* No links to GitHub repositories, live deployments, or project demos.
* *Note:* Metrics must be authentic. If an app was a personal project without users, describe the technical outcome rather than inventing metrics.

### 4. Project Selection is Not Justified
* 3 projects listed without alignment to any specific role or specialty.
* Does not showcase John's best capabilities.
* 2–3 well-explained projects are vastly superior to multiple shallow tutorial projects.

### 5. Achievements Section Contains Filler
* *"Participated in hackathons"* — vague; omits event name, project built, team role, or outcome.
* *"Interested in coding"* — a hobby/attitude, not an achievement.
* *"Good problem solver"* — an unsupported self-proclamation.

### 6. No Targeting or Clear Direction
* Lacks alignment with a specific domain (software engineering, data science, web development).
* Skills and projects are not prioritized for any specific job profile.

### 7. Limited Evidence of Ownership
* Impossible to discern individual contributions versus copied boilerplate or team tasks.
* Does not show engineering maturity or problem-solving capability.

### 8. Imprecise Technical Terminology
* *"Node"* instead of standard *"Node.js"*.
* *"ML Disease Prediction"* is too ambiguous to evaluate.

### 9. Section Layout & Contact Gaps
* Only lists physical location ("Bangalore, India") — lacks email, phone, GitHub profile, and LinkedIn URL.
* No Positions of Responsibility or Experience section (these are optional, but should be considered if evidence exists).

### 10. Recruiter Diagnostic Questions
Facilitators can ask these direct questions to the room:
1. *What exactly did you build in the e-commerce website?*
2. *Which components did you personally code?*
3. *What does the disease prediction model predict, and how did you measure accuracy?*
4. *Why did you choose MongoDB over PostgreSQL?*
5. *Can you show me the GitHub code for these projects right now?*
6. *Which of these 15 skills could you answer a technical whiteboard question on today?*
7. *What was the outcome of the hackathon you attended?*
